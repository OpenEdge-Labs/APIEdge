# ADR 0011: Release packaging, SBOM and signing

- Status: accepted
- Date: 2026-11-02
- Task: T-016

## Context

APIEdge ships as one-click installers for Windows, macOS and Linux, a pip wheel, a container image
with Docker Compose, and a Helm chart (PROJECT_GUIDE, "Cross-platform shipping"). Each release
also needs checksums, signatures and a CycloneDX SBOM. Constraints: third-party packages are
never committed or bundled, every dependency install is hash-checked, only Apache-2.0-compatible
licenses are allowed, and nothing is published (PyPI, registries, public GitHub releases) until
the customer sets up publishing (T-031).

## Decision

1. **One stdlib-only release script**, `scripts/build-release.py`, builds and checks everything:
   the wheel (`pip wheel --no-build-isolation` with the hash-locked setuptools from `build.lock`,
   then a content check: console, migrations, LICENSE/NOTICE present, no foreign top-level
   packages); one installer zip per OS, built only from git-tracked files (APIEdge source, the
   prebuilt console, hash locks, docs and that OS's launcher, with Unix modes kept); the SBOM; the
   Helm chart; and `SHA256SUMS`. It also verifies a release directory and smoke-tests an installed
   wheel (reusing the installer's health check).
2. **The SBOM is generated by our own code**, not by a CycloneDX tool. It lists the pins of
   `runtime.lock` (licenses read from the installed distributions with the same function as the
   license gate) and the production npm packages bundled into the console (with their lock
   integrity hashes). This avoids adding a tool and its transitive dependencies to the dev lock
   for a document whose content we already have. It covers CycloneDX 1.5 fields that scanners
   use (purl, version, licenses, hashes, dependencies) and is checked by unit tests.
3. **Signing is a GPG detached signature of `SHA256SUMS`**, which covers every artifact. The
   workflow signs only when the `APIEDGE_RELEASE_GPG_KEY` (and passphrase) secrets exist and
   otherwise logs a notice. Keyless Sigstore attestations were not chosen because they need a
   public repository or GitHub Enterprise Cloud for a private one.
4. **Container image**: a two-stage build on `python:3.12-slim` pinned by multi-arch digest, a
   venv filled with `--require-hashes`, non-root user 10001, data volume `/var/lib/apiedge`, a
   `/healthz` health check, and an entry point that migrates, ensures the first SuperAdmin
   (password from a secret file, or generated and shown once) and starts the console and gateway.
   Built for linux/amd64 and linux/arm64 in CI; not pushed.
5. **Compose uses PostgreSQL 17 and Valkey** (BSD-3-Clause, Redis-compatible) instead of Redis 8,
   whose server is no longer under a permissive license. Images are pinned by digest; there are
   no default passwords; ports are bound to localhost.
6. **PostgreSQL driver only in the compose-built image**: `packaging/docker/postgres-driver.txt`
   hash-pins psycopg 3 and is installed only with `--build-arg APIEDGE_WITH_POSTGRES=1`. It is
   not added to `runtime.lock`: that is proposal VP-002, which needs the customer's decision and a
   license review (psycopg is LGPL-3.0). *Superseded in T-033 (2026-11-05): the customer chose
   pg8000 (BSD-3-Clause, pure Python) in `runtime.lock`; the build argument and
   `postgres-driver.txt` were removed and there is one image variant.*
7. **Helm chart**: one replica with `Recreate`, because SQLite and the key file live on a
   ReadWriteOnce volume; secrets only from existing Kubernetes Secrets; restricted pod security.
8. **Release workflow** (`.github/workflows/release.yml`) runs on `v*` tags, on manual dispatch,
   and on pushes or pull requests that touch packaging files. It builds once, then tests the
   artifacts themselves: each OS bundle is unzipped and installed unattended with a health check,
   re-run (upgrade path) and uninstalled; the wheel is installed into a clean venv on three OSs
   and two Python versions and health-checked; the image is built for both architectures and
   smoke-tested; the compose stack is started and a sign-in against PostgreSQL is made; the chart
   is linted and rendered. Publishing is a separate job that runs only for a tag when the
   repository variable `APIEDGE_PUBLISH_RELEASE` is `true`, and creates a draft release.

## Consequences

- A release is reproducible from a tag: the tag must equal `v<pyproject version>`, archive
  timestamps come from the commit, and every input is pinned.
- Until the customer provides a signing key and enables publishing (T-031), artifacts are
  checksummed and downloadable from the workflow run only, not signed or published.
- The SBOM generator must be kept in step with the CycloneDX specification ourselves.
- PostgreSQL works out of the box only in the compose stack; installer and wheel users install
  the driver themselves until VP-002 is decided.

# ADR 0015: Built-in OAuth 2.0 authorization server and OpenID Connect provider

- Status: accepted
- Date: 2026-11-06
- Task: T-023

## Context

T-023 asks for a built-in OAuth 2.0 authorization server (client credentials, authorization code
with PKCE, refresh, introspection, revocation), OpenID Connect and JWT generation. APIEdge is
multi-tenant, so every tenant needs its own issuer, keys and clients, and no tenant's clients or
tokens may work for another. The runtime set has no OAuth library, and the license and wheel
rules (ADR 0002, ADR 0013) favour building on the already-locked pycryptodome.

## Decision

- **One authorization server per tenant**, served by the gateway under
  `/<tenant slug>/oauth2/` (discovery, `jwks`, `authorize`, `token`, `introspect`, `revoke`,
  `userinfo`). The issuer is `<APIEDGE_GATEWAY_PUBLIC_URL>/<tenant slug>/oauth2`. API base paths
  may no longer start with `/oauth2`.
- **Signing keys**: RSA 2048 / RS256 per tenant, generated by APIEdge; private keys are stored only
  encrypted with the secrets box (AES-256-GCM, bound to tenant and key id). Rotation makes a new
  key active and keeps earlier keys in the JWKS ("retired") until an administrator deletes them.
  A tenant's first client creates its first key.
- **Clients**: confidential (secret shown once, stored as SHA-256) or public (no secret,
  authorization code only). Redirect URIs match exactly and must be https, loopback http
  (RFC 8252) or a reverse-domain private scheme. Grant types, scopes, audiences and token
  lifetimes are set per client.
- **Grants**: `client_credentials` (confidential clients only, no refresh token),
  `authorization_code` with mandatory PKCE `S256` for every client, and `refresh_token`.
  Authorization codes live 60 seconds and are single-use; refresh tokens are opaque, stored
  hashed and rotated on every use. Presenting a used code or refresh token revokes every refresh
  token of that sign-in (reuse detection) and is audit-logged.
- **Tokens**: access tokens are RS256 JWTs (`typ: at+jwt`; `iss`, `sub`, `client_id`, `scope`,
  `aud`, `exp`, `iat`, `nbf`, `jti`); ID tokens for the `openid` scope carry `nonce`, `auth_time`,
  `azp` and, by scope, `preferred_username` and `email`.
- **End-user sign-in** (customer decision): the people who sign in at `authorize` are the
  tenant's console users, behind a pluggable `UserRegistry` interface
  (`apiedge.security.user_registry`) so LDAP or other registries can be added later. The console
  registry reuses the console's password hashing, lockout and TOTP. The sign-in page is rendered
  by the server with a strict CSP (`form-action` limited to the page and the client's redirect
  origin, `frame-ancestors 'none'`), a SameSite=Strict CSRF cookie and per-address throttling.
  There is no consent screen: clients are registered by the tenant's administrators
  (first-party clients).
- **Revocation and introspection**: refresh tokens are revoked by family, access tokens by `jti`
  (kept until they would expire). Introspection is for the tenant's confidential clients and
  reflects revocation. The `jwt` policy's **built-in issuer** option validates tokens locally
  against the tenant's JWKS and issuer (loaded with the gateway configuration and reloaded when
  keys change); it does not consult the revocation list, so access tokens should stay
  short-lived (default 10 minutes).

## Consequences

- Tokens of one tenant never validate for another: keys, issuers, clients and the user registry
  are all per tenant, and every database access runs on a tenant-bound session.
- The issuer URL is part of every token, so `APIEDGE_GATEWAY_PUBLIC_URL` must be set before
  tokens are issued in production; changing it invalidates outstanding tokens for policies that
  check the issuer.
- The token endpoint has no CORS support yet, so browser-based public clients need a
  backend-for-frontend or a same-origin proxy; native and server-side clients are unaffected.
- Not included yet: dynamic client registration, consent screens, `private_key_jwt` client
  authentication, pushed authorization requests and encrypted tokens.

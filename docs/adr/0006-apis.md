# ADR 0006: APIs, upstreams and routes inside products

- Status: accepted
- Date: 2026-11-01
- Task: T-006

## Context

APIs are the third level of the domain model (Tenant > Product > API > Route). The gateway
runtime (T-007) will serve them, so the configuration has to be unambiguous to route and safe to
proxy to. Upstream URLs are outbound targets and therefore an SSRF risk (OWASP A10 / API7).

## Decision

* New tenant-owned tables `apis`, `api_upstreams` and `api_routes` (migration 0004). An API has a
  name, a version, a base path, a description, an upstream timeout and a lifecycle. Upstreams
  (URL and weight 1-100) and routes (HTTP methods and a path relative to the base path) are child
  rows kept in order.
* The admin API exposes an API as one document: `POST` and `PATCH` carry the upstream and route
  lists and `PATCH` replaces them. This matches the no-code form editor, which edits an API as a
  whole, and keeps a single audit event per save.
* The base path is unique within the tenant (across all products), so the gateway can resolve a
  request without ambiguity; name and version are unique within the product. Paths the server
  answers itself (`/api/v1`, `/healthz`, `/readyz`, `/docs`, `/redoc`, `/openapi.json`, `/assets`)
  are reserved. Route paths support `{name}` parameters and a final `/*` prefix wildcard; two
  routes may not match the same method and path.
* Every upstream URL passes `apiedge.security.ssrf.check_url` under the configured policy
  (`Settings.ssrf_policy()`) when it is saved. The admin API answers with a fixed message instead
  of the guard's exception text. T-007 must check again when it connects (DNS can change).
* Authorization reuses the product model of ADR 0005: `api:*` permissions held tenant-wide or
  through a grant scoped to the product. A product whose APIs the caller cannot read, and an API
  that does not belong to the product in the path, answer 404.
* Lifecycle as for products. Publishing needs at least one upstream and one route; a published API
  keeps its base path and cannot drop to zero upstreams or routes. Retired APIs are read-only and
  only draft or retired APIs can be deleted. In a retired product the APIs are read-only but can
  still be deprecated and retired, so that the product can be emptied. A product that still
  contains APIs cannot be deleted.

## Consequences

* T-007 reads published and deprecated APIs (of products that are not retired) from these tables.
* Load-balancing algorithms, retries, health checks and TLS settings are left to T-007 and T-025;
  the weight and timeout fields are their starting point.
* T-011 (OpenAPI import) creates APIs through the same validation.
